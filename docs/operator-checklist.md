# GreenTokens test day: operator checklist (this PC is the server)

This PC runs the GreenTokens server for the test: database, storage, scheduler and API, reached by
providers and Databricks through a public tunnel address. Provider computers only connect outward to it.

## Before the test (on this PC)
1. **Docker Desktop is running.** Keep this PC **plugged in and awake**: Settings → System → Power → sleep: Never.
2. **Start the server:** in the project folder:
   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts\start_server.ps1
   ```
   It starts the backend and tunnel as background processes, prints the **server address**, and updates
   your Databricks secret `greentokens/url`. Keep this computer awake during the test.
3. **Configure the app once for this PC's public address.** `start_server.ps1` updates the public address in `apps/provider_app/provider-server.json` and the desktop connection policy. To do it manually from `apps/provider_app`:
   ```powershell
   node scripts/configure-server.mjs https://YOUR-CURRENT-TUNNEL.trycloudflare.com
   ```
   This address is public, not a credential. The installer includes it so owners never enter it. GitHub builds can override it with the repository variable `GT_PROVIDER_SERVER`. A local build uses the checked-in configuration. Build/release still needs to happen before owners can download this version.
4. **Send each owner the new installer link and `docs/provider-guide.md`.** They create their own username/password and sign in. No provider accounts or codes need to be generated by you. `scripts/add_account.py --customer` is still available for Databricks credentials; old API keys continue to work.

## Upgrading the backend
The launcher applies additive migration `0003` for provider accounts, sessions, and login throttling. Restart an older backend to load the new routes. Existing jobs, provider keys, and Databricks accounts are preserved. `start_server.ps1` detects an old running API and reports that a restart is needed.

## During the test
- **Who is connected:**
  ```powershell
  .\.venv\Scripts\python.exe -m scripts.providers
  ```
  You want each RTX PC **online** with **NVIDIA GeForce RTX 5070** in the GPU column. If it says
  "not usable yet", that owner needs a newer NVIDIA driver, then Settings → Repair setup.
- **Train as the customer (Databricks):** open `GreenTokens/01_Submit_Training_Job`, template `text_finetune_v1`,
  model `prajjwal1/bert-small`, GPU `yes`, Run all, then copy the job id. Open `02_View_Results`, paste it and run.
  Run `01` three times to keep all three computers busy; each job goes to one free computer.

## Important limits
- **The tunnel address can change if the tunnel restarts.** Existing installers keep their built-in address. Reconfigure and rebuild the app for the new address (or arrange a permanent hostname later). Keep the tunnel running all test day. Accounts remain in this PC's database; no new codes or accounts are needed.
- One job runs on one computer; three computers = three jobs at once (not one model split across three).
- Only approved workloads run (`text_finetune_v1`). Customer repositories can't run yet.
- No Linux installer yet.

## After the test
Stop the backend and cloudflared processes you started for this test (Task Manager). To stop the database: `docker stop greentokens-dev-mysql greentokens-dev-storage`.

## Account behavior and pilot limits
- Provider sign-up is open. Every new account has only the provider role, with its own organization; it cannot submit customer jobs or access another customer's artifacts. Self-registration does not verify a provider's hardware, identity, or returned training results. Use only known owners and non-sensitive test workloads for this pilot.
- Passwords use salted scrypt hashes. Only hashes of random session tokens are stored server-side. Sessions are tied to a computer ID, expire after 24 hours, and can be revoked by sign-out. The app keeps credentials only in memory, requiring sign-in after reopening.
- Login/signup have database-backed rate limits. Only the configured desktop origins and the local Vite preview origin are allowed to call auth from a browser.
- Password recovery, account deletion UI, email verification, and persistent OS-keychain sign-in are not implemented. Existing invite accounts are not automatically converted; owners create a new account and sign in. A computer's new login identity is tracked separately from any earlier invite enrollment.
